# 軍儀(Gungi) 設計書

## 概要

`games/gungi/` に実装した、HUNTER×HUNTER作中に登場する架空のボードゲーム「軍儀」のP2P対戦版。

原作では駒の動き・配置などの細則が全ては公開されていないため、この実装は以下を参考にファンが再構成した**非公式ルール**である。

- HUNTER×HUNTER 軍儀 Q&A(Universal Music)
- note.com「軍儀・ルール解説」シリーズ(源川さとし氏)ほか、ファンによる軍儀考察記事(ロジーさん,PhD氏など)
- YouTube「HUNTER×HUNTER 軍儀 4分で分かる遊び方」

公式に断片的にしか分からない部分(段数によるマス数の伸び方の一部、謀の寝返りの詳細な処理手順など)は、遊びやすさと内部整合性を優先して独自に補完している。ゲーム内ヘルプ(index.htmlの「📖 ルール」モーダル)にも同様の断り書きと出典を明記している。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `pieces.js` | 駒定義(移動ルール)と移動生成エンジン。DOM非依存の純粋ロジック。Node.js/ブラウザ両対応(UMD風) |
| `engine.js` | ゲーム状態管理。配置フェーズ・本戦フェーズ・勝敗判定・千日手判定など。`pieces.js` に依存。Node.js/ブラウザ両対応 |
| `ai.js` | 1人プレイ用AI。`engine.js` の合法手列挙をそのまま使い、静的評価関数による貪欲法で一手を選ぶ。Node.js/ブラウザ両対応 |
| `ui.js` | 盤面・持ち駒トレイ・モーダル等のDOM描画。状態を受け取って描画するだけの純粋な描画層 |
| `net.js` | PeerJSによるP2P通信(pongと同じ「合言葉」方式)。ルーム参加・データ送受信のラッパー |
| `main.js` | 画面遷移・クリック操作の判定・ネットワークアクション/AIの手番の送受信を繋ぐ制御層 |
| `index.html` / `style.css` | ページ構造とスタイル |

`pieces.js` と `engine.js` はNode.js上で `require()` して単体テストできるように設計されている(UI層と分離することで、盤面ロジックの正しさをブラウザなしで検証可能)。

## 盤面とコマの表現

- 盤は9×9(x=1..9, y=1..9)。
- 各マスには最大3段(ツケ)まで駒を積める。`board[x][y]` は下段→上段の配列。
- 先手(Player 0)の自陣は y=1〜3、後手(Player 1)の自陣は y=7〜9。「前方(F)」は各プレイヤーから見て敵陣方向。
- 後手側の移動方向ベクトルは、先手側の方向ベクトルを180度回転(dx,dyともに反転)させて算出する(`pieces.js` の `worldVector`)。全駒が左右対称な射程を持つため、この回転だけで正しく動く。

## 駒一覧(全14種・計25枚)

段数(ツケの高さ)が上がるほど射程が伸びる。表の数値は「1段目→2段目→3段目」の移動可能マス数。

| 駒 | 枚数 | 種別 | 移動ルール |
|---|---|---|---|
| 帥(すい) | 1 | 通常(全方向) | 8方向すべて 1→2→3。**取られたら敗北** |
| 謀(はかる) | 1 | 特殊 | 8方向すべて 1→2→3。**★寝返り能力を持つ(後述)** |
| 大(たいしょう) | 1 | 通常 | タテヨコ無制限、ナナメ 1→2→3 |
| 中(ちゅうじょう) | 1 | 通常 | タテヨコ 1→2→3、ナナメ無制限 |
| 小(しょうしょう) | 2 | 通常 | 前・左前・右前・左・右・後(金将型) 各1→2→3 |
| 砦(とりで) | 2 | 通常 | 前・左・右・左後・右後(斜め前と真後ろが無い) 各1→2→3 |
| 兵(ひょう) | 4 | 通常 | 前・後 各1→2→3 |
| 侍(さむらい) | 2 | 通常 | 左前・右前・後 各1→2→3 |
| 槍(やり) | 3 | 通常 | 前2→3→4、後1→2→3、左前1→2→3、右前1→2→3 |
| 忍(しのび) | 2 | 通常 | 左前・右前・左後・右後 各2→3→4 |
| 馬(うま) | 2 | 通常 | 前・後 各2→3→4、左・右 各1→2→3 |
| 弓(ゆみ) | 2 | ★特殊(飛越え) | 前・後・左・右 各3→4→5、自分の段以下のスタックを飛び越えられる |
| 砲(おおづつ) | 1 | ★特殊(飛越え) | 前・後・左・右 盤端まで、自分の段以下のスタックを飛び越えられる |
| 筒(つつ) | 1 | ★特殊(飛越え) | 左前・右前・左後・右後 盤端まで、自分の段以下のスタックを飛び越えられる |

「通常」10種・25-5=20枚、「★特殊」4種(謀・弓・砲・筒)・5枚、合計25枚。

### 移動生成の実装(`pieces.js`)

- **slider(通常駒)**: 各方向に射程距離まで直進。空マスは通過可、自駒に当たったら(段が3未満なら)「ツケ」として止まる、敵駒に当たったら段条件を満たせば「捕獲」として止まる。いずれの場合も、その駒より先には進めない。
- **rider(大・中専用)**: タテヨコ/ナナメの一方が無制限、他方が段数依存。slider同様に自駒/敵駒で停止。
- **jumper(弓・砲・筒)**: 自分の現在の段以下の高さのスタック(敵味方問わず)は透過して飛び越えられる。自分より高い段のスタックには遮られて進めない。敵の透過可能なスタックの上には着地(捕獲)も選択できる。

### 捕獲ルール

- スタックの中で動かせるのは**常に最上段の駒のみ**。
- **自分より高い段にある相手の駒は捕獲できない**(移動元の駒の段 ≥ 相手駒の段が必要)。
- 捕獲すると、相手の最上段の駒だけが除去され、自分の駒がその段(高さ)に入る(下の駒はそのまま残る)。
- 捕獲された駒は将棋と異なり**持ち駒には戻らず、完全にゲームから除外**される(実装上は表示用に `graveyard` へ記録するのみ)。

## 対局の流れ

### 1. 配置フェーズ(`phase: 'placement'`)

- 先手・後手が交互に、自陣3列(9マス×3段)へ持ち駒を1枚ずつ配置する。
- **各プレイヤーが最初に置く駒は必ず「帥」**(`engine.place` が強制)。
- 「配置完了(済)」を宣言すると、以後そのプレイヤーの配置ターンはスキップされる。両者が完了を宣言した時点で本戦フェーズへ移行し、先手から手番を開始する。
- 「残りをお任せ配置」ボタン(`autoFillRemaining`)で、既定フォーメーション(後述)に沿って残りの持ち駒を一括配置できる。

### 2. 本戦フェーズ(`phase: 'play'`)、手番でできる3つの行動

1. **移動**: 自分のスタック最上段の駒を移動ルールに従って動かす。移動先が空マスなら通常移動、自分の駒の上ならツケ、相手の駒の上なら(段条件を満たせば)捕獲。
2. **新(アラタ)**: 持ち駒を盤上の空マス(自陣に限らずどこでも)へ新規配置する。
3. **謀の寝返り**(★このゲーム独自の解釈): 「謀」を持ち駒に残した状態で、盤上の敵駒(帥を除く)と**同じ種類の駒も自分の持ち駒にある**場合、その2枚(謀+同種駒)を消費して、対象の敵駒を自分の駒に寝返らせる。段の高さは変わらない。敵の「帥」は対象にできない。

いずれの行動も、実行後に自分の帥が王手状態になる場合は選択できない(`wouldSelfCheck` による事前シミュレーション判定)。

### 3. 勝敗・終局判定

- 相手の「帥」を捕獲した時点で即勝利。
- 手番が回ってきたプレイヤーに、王手を解消できる合法手が一つも無ければ**詰み**で敗北(`allLegalActionsExist` が false の場合)。合法手が存在しない状態は王手の有無に関わらず敗北扱い(パスができないため)。
- **千日手**: 同一局面(盤面+持ち駒+手番)が4回発生した場合は引き分けとして対局終了(`positionHash` による局面のハッシュ管理)。指し直しではなく引き分け表示とする簡略化を行っている。
- 投了(`resign`)、通信切断時のリロードにも対応。

## 既定フォーメーション(お試しプレイ・お任せ配置)

固定配置の初期配置は、note.comの軍儀考察記事に掲載されていた配置例をそのまま採用した(ユーザーが記事のスクリーンショットを提示し、それに合わせて `DEFAULT_LAYOUT` を作成)。

- 25枚中**15枚のみ**を下記のフォーメーションで配置し、**残り10枚(小×2・槍×2・馬×1・忍×1・兵×1・砲×1・筒×1・謀×1)は持ち駒として残したまま本戦を開始**する(将棋のように全駒を並べきる方式ではない)。
- 自陣3列を「奥列(offset0)・中列(offset1)・前列(offset2)」として表現(`engine.js` の `DEFAULT_LAYOUT`)。

| 列 | 配置(x座標:駒種) |
|---|---|
| 奥列 | 4:中, 5:帥, 6:大 |
| 中列 | 2:馬, 3:弓, 5:槍, 7:弓, 8:忍 |
| 前列 | 1:兵, 3:砦, 4:侍, 5:兵, 6:侍, 7:砦, 9:兵 |

後手側は同じテンプレートをoffset反転(奥列→y=9、前列→y=7)で適用するのみで、x座標・駒種はそのまま流用する(全駒が左右対称のため反転不要)。

帥がテンプレート枠に置けなかった場合(手動配置と併用した場合など)に備え、`autoFillRemaining` は帥だけは自陣の空きマスへ確保してから配置完了とする安全策を持つ。

## UI設計上の工夫

- **駒の重なりを分かりやすくする**(要件として明示された点)ため、以下を組み合わせている:
  1. スタック内の各段を少しずつ右上へオフセットして重ね描画(下の駒の端が覗いて見える)
  2. 右下に「×段数」バッジを表示
  3. どのマスをクリックしても右サイドパネルの「選択中マスの詳細」に、下段→上段の内訳(所有者・駒種)を一覧表示
- 盤面は各プレイヤーの視点に合わせて描画(自陣が常に画面手前/下側に来るよう、後手側は列・行ともに反転して表示)。
- 移動先ハイライトは種類ごとに色分け(通常移動=緑、ツケ=青、捕獲=赤い輪、新=紫、寝返り=紫の破線の輪)。
- 王手中は自分の帥のマスがパルスアニメーションで警告表示される。

## ネットワーク設計

- pongと同じ「合言葉」方式: `gungi-{合言葉}-1`(ホスト)/ `gungi-{合言葉}-2`(ゲスト)のPeerJS IDで自動マッチング。
- ターン制ゲームのため、pongのような「毎フレーム全状態を送る」方式ではなく、**行動(アクション)単位でメッセージを送受信し、両クライアントが同一の決定的ルールエンジンをローカルで実行する**方式を採用。
  - 送信するアクション種別: `place`(配置) / `pass`(配置完了) / `autofill`(お任せ配置) / `move`(移動) / `arata`(新) / `turncoat`(寝返り) / `resign`(投了) / `REMATCH`(再戦)
  - 盤面全体を都度送らないため通信量が少なく、双方のロジックが同一である限り状態は自然に同期する。
- 対局モード(自由配置/固定配置)はホスト側が選択し、`MODE` メッセージで通知。ゲスト側は受信したモードに応じて同じ手順(必要なら `quickStartBothDefault`)をローカルで実行して同じ初期状態を再現する。

## 1人プレイ(AI対戦)モード

- トップ画面から「1人プレイ」を選ぶと、PeerJSに一切接続せずローカルの `state` だけで対局が完結する(`Net.send` は接続が無ければ黙って何もしないため、通常の行動コミット処理をそのまま流用できる)。
- 対局前に「手番(先手/後手)」「AIの強さ(弱い/普通/強い)」「配置方式(自由配置/固定配置)」を選択する。自由配置を選んだ場合、AI側の配置は既定フォーメーション(`autoFillRemaining`)を1回のアクションでまとめて行い、人間側だけ通常通り1枚ずつ手動配置する。
- `main.js` の `triggerAiTurn()` が、人間の行動後(`afterLocalAction`)および対局開始直後に「今AIの手番か」を確認し、該当すればタイマー(0.45〜1秒のランダム遅延で「考えている感」を演出)を挟んで `ai.js` の `chooseAction` を呼び、結果を通常の `Engine.move` / `arata` / `turncoat` として適用する。

### AIのアルゴリズム(`ai.js`)

- 深い探索(2手読み以上)は行わず、**静的評価関数による貪欲法(1手読み)**を基本とする。理由: 軍儀はスタック構造・新(アラタ)・寝返りがあるため1手番あたりの合法手数が数百に達することがあり、`engine.js` の合法手列挙自体が自玉の安全性を毎回シミュレーションする重めの処理のため、素直な2手読みは組み合わせ爆発しやすい。
- 評価関数: 盤上の自駒/敵駒の価値合計(段が高いほど僅かに加点)+持ち駒の価値(割引)+王手中かどうかの補正。駒の価値は射程・特殊能力のおおよその強さを反映した目安値(帥は実質無限大、大/中=9、砲/筒=7など)。
- 難易度による違い:
  - **弱い**: 合法手からの重み付きランダム選択(捕獲・寝返りを少し優先する程度で、明確な悪手も指す)
  - **普通**: 全合法手を静的評価し、最善手に近い(僅差の)候補からランダムに選ぶ(単調な最善手固定を避けるため)
  - **強い**: 常に最善手を選択。さらに、移動・配置した駒が直後に相手の攻撃範囲に入っていないか(タダ取りされないか)を1手分だけ追加でチェックし、該当すれば減点する簡易的な「駒の安全確認」を行う

## 既知の簡略化・非公式解釈まとめ

- 謀の「寝返り」の具体的な処理(持ち駒2枚を消費し、対象駒の所有者だけを書き換える)は公式に明言されていないため、本実装独自のルールとして定義した。
- 千日手は「指し直し」ではなく「引き分け表示+再戦ボタン」に簡略化している。
- 打ち歩詰め(将棋における「歩の新で詰ませてはいけない」ルール)に相当する制限は、軍儀での存在が確認できなかったため実装していない。
- 小・砦などの段数によるマス数の伸び方(前方向のみ伸びるか、全方向均等に伸びるか等)は、参考記事で明言されていない部分は「射程を持つ全方向が段数と同じだけ均等に伸びる」という単純なルールで統一した。
